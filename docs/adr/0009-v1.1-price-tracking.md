# 0009 — v1.1 price tracking: bulk refresh, 52W, prev_close, snapshot-aware UX

## Status

Accepted (v1.1)

## Context

v1 stores `current_price` per holding as a manual cache: the user types it into the form, or it gets stale. There is no 52-week high/low, no previous close, no Day Δ%, no automated refresh. The form is the only source of truth for prices.

v1.1 introduces automated price refresh from Yahoo Finance, plus fields that support richer portfolio visibility:

- **3 new per-holding fields**: `high_52w`, `low_52w`, `prev_close`
- **One-click bulk refresh** from Yahoo Finance batch endpoint
- **Day Δ% + 52W range bar** in the holdings table
- **Intraday-aware snapshot UX** (light warning when capturing during open market)
- **Schema version bump** to `1.1` (load-time, non-destructive)

The architectural questions this ADR answers are about **how** to wire these features, not **what** they are. The schema spec is in [`.scratch/price-tracking/schema-section.md`](../.scratch/price-tracking/schema-section.md); the full specification is in [`.scratch/price-tracking/spec.md`](../.scratch/price-tracking/spec.md).

The Yahoo Finance choice itself (unofficial API, no API key) is established in [ADR 0001](0001-yahoo-finance-prices.md). This ADR assumes that and layers v1.1-specific decisions on top.

## Decision

### 1. Yahoo batch endpoint for bulk refresh

**Use `/v7/finance/quote?symbols=A,B,C` with one request per refresh.** All holdings supplied in a single API call.

**Rejected**: per-symbol fetch (one URL per holding). Reasons: N+1 network calls, N× the latency, N× the cookie/crumb round-trips, and Yahoo's batch endpoint already exists and supports mixed US+TW+FX symbols.

**Rejected**: per-row refresh button. Reasons: clutters the table, encourages users to refresh single holdings (which is rarely what they want — they want a coherent snapshot of the whole portfolio), and feeds the per-symbol-fetch anti-pattern.

**Rejected**: auto-refresh on page load or on a timer. Reasons: indistinguishable from "stale by definition" without regular refresh, and silently does N network calls whether the user wants them or not. Manual button preserves user intent.

Yahoo's crumb auth flow (cookie from `fc.yahoo.com`, crumb from `/v1/test/getcrumb`, append `&crumb=...` to every quote call) is a known dependency of the unofficial API since late 2024. Implementation lives in `lib/yahoo.js` with DI for testability.

### 2. Auto-retry 5x with cancel-by-click

**On any per-symbol failure, retry the failed subset up to 5 times with exponential backoff (1s, 2s, 4s, 8s, 16s).** If the user clicks the refresh button again during retry, the retry loop exits at the next iteration but in-flight fetches are not aborted (fetch has no clean abort in browsers; we don't introduce one).

**Rejected**: fail-fast on first failure. Reasons: Yahoo's silent-drop behavior for invalid symbols means a single typo can pollute the whole refresh; auto-retry makes transient errors invisible.

**Rejected**: no retry (silent failures). Reasons: user clicks "refresh", gets nothing to show for it, doesn't know why. Auto-retry raises the success rate to ~100% for transient failures.

**Rejected**: retry forever. Reasons: 5 attempts is enough for transient blips; beyond that it's a real outage and the user should see the red badge / "Retry N failed" button.

**Rejected**: abort in-flight fetch on cancel. Reasons: `AbortController` adds complexity, and the timing window is small (the in-flight fetch is usually seconds). Best-effort delay is acceptable.

### 3. Partial success is the default

**A refresh that returns some symbols and drops others is treated as partial success: successful holdings update, failed holdings get a red badge, and the retry path re-fetches only the failed subset.**

**Rejected**: all-or-nothing. Reasons: a single bad ticker shouldn't block the entire refresh; the user gets more value from "16 of 17 holdings updated" than "nothing updated."

**Rejected**: continue retries but never surface failures. Reasons: silent failures are worse than visible ones; the user must be able to see when a holding is stale.

### 4. Red badge in-memory only

**Failed holdings show a red badge until the next successful refresh of that holding. The badge is an in-memory state, not persisted.**

**Rejected**: persist `refresh_failed` as a schema field. Reasons: it's transient UI feedback; persisting it would survive unload and confuse the user on next session (a holding marked "failed" might be fine once Yahoo's symbol list updates). The schema stays small.

### 5. Manual override always allowed; refresh overwrites

**The form fields for `current_price`, `high_52w`, `low_52w`, `prev_close` are editable. Refresh overwrites manual values without warning.**

**Rejected**: warn before overwriting. Reasons: the user clicked refresh, the explicit intent is to overwrite. Friction here breaks the "one click refreshes" promise.

**Rejected**: make fields read-only when fetcher is available. Reasons: the user must be able to escape Yahoo errors (e.g., a Yahoo typo in their portfolio file). The form is the universal escape hatch.

**Rejected**: hide fields and only show "N/A" until first fetch. Reasons: defeats the purpose of the cache; makes the app non-functional before the first refresh.

### 6. Lazy populate migration; load-time version bump

**v1.0 files load by v1.1 app: shallow-merge with `defaultPortfolio()` to add `high_52w`, `low_52w`, `prev_close` (default `null`). `version` is set to `'1.1'` immediately on load, before any save.**

**Rejected**: bump version on first successful refresh. Reasons: conflate schema version with data state. After the shallow-merge, the in-memory data IS v1.1-shaped; the version field reflects that.

**Rejected**: ask user to confirm migration. Reasons: the migration is non-destructive (no existing values touched), and the user does not need to "approve" a change that is purely additive.

**Rejected**: keep version as `'1.0'` for backward compatibility. Reasons: confuses the version field with "what the user has done" rather than "what schema we conform to." v1.0 app loading v1.1 file ignores extra fields anyway — that compatibility is one-directional and unaffected by the version string.

UI hint: when `high_52w = null`, the 52W range bar shows `—` (em dash); when `prev_close = null`, the Day Δ% shows `—`. The user is nudged to click refresh.

### 7. Snapshot schema unchanged

**Snapshots store only `current_price` per holding. 52W high/low and prev_close are NOT included.**

**Rejected**: include 52W + prev_close in snapshots. Reasons:
- 52W high/low is a moving reference window; charting a moving reference across time is less meaningful than charting the price itself.
- `prev_close` duplicates information derivable from the previous snapshot's `current_price` when snapshots are taken at market close.
- Keeps the snapshot schema small and stable for the future Snapshot UI effort.

**Rejected**: skip snapshot storage entirely when intraday. Reasons: the user wants to capture a snapshot; the warning is informational, not a gate. We store anyway. (See decision #8.)

### 8. Intraday snapshot: store + light UI warning

**When the user takes a snapshot, if ANY holding's market is in an active session (pre, regular, post, including extended), show a confirm dialog: "現在盤中，價格會波動，要繼續嗎？" The user can cancel or proceed; either way, intraday pricing is recorded.**

**Rejected**: block snapshot during intraday. Reasons: the user has a reason; we shouldn't second-guess. A warning is sufficient.

**Rejected**: no warning. Reasons: "現在這時間點的價格是 110" vs "收盤價是 115" looks like a 5% loss when it's actually just timing. The user needs to know what's happening.

**Rejected**: hardcode market hours per exchange (TWSE 9:00-13:30, NYSE 09:30-16:00 ET). Reasons: requires per-exchange tables, DST math, holiday handling. Yahoo's `marketState` field already encodes all of this.

**Rejected**: use a third-party holiday API (e.g. nager.date). Reasons: Yahoo's `marketState` already covers holidays (verified on MLK Day, Thanksgiving, Presidents Day). nager.date is incomplete (TW returns 204) and inaccurate (US list includes Good Friday, which is not a NYSE holiday).

**FX exception**: `quoteType === 'CURRENCY'` (e.g. `TWD=X`) is excluded from intraday detection. Yahoo reports `REGULAR` 24/7 for FX, but FX doesn't have a meaningful intraday concept.

### 9. Holdings table UX: Day Δ% + 52W range bar, NOT 3 raw columns

**Day Δ% as a numeric column (color-coded green/red, 2 decimals, `%` suffix). 52W range bar as an inline visual bar showing where current price sits in `[low_52w, high_52w]`.**

**Rejected**: 3 raw numeric columns (52W high, 52W low, prev_close). Reasons:
- The user's question is "how is this holding doing?", not "what are the absolute 52W high/low values?"
- 3 columns of dense numbers in a portfolio table are noise.
- Day Δ% answers "what happened today?"; the range bar answers "where are we in the range?"; both are visualizations of the same 4 source fields.

**Rejected**: only Day Δ%, no range bar. Reasons: the 52W range is genuinely useful for understanding volatility and position; the bar visualizes it cheaply.

**Rejected**: Line chart or sparkline. Reasons: out of scope (v1.1 snapshot UI is separate effort); the range bar is a 1-D projection that conveys the same "where are we" insight at a fraction of the visual cost.

### 10. Header layout: frequency grouping + HTML `<details>`

**High-frequency actions (refresh, sync, currency toggle) stay inline in the header. Low-frequency actions (FX rate, import, export) collapse into a `...` menu implemented as a native HTML `<details>` element.**

**Rejected**: keep all buttons inline. Reasons: 6 buttons in a header is too many on mobile (the sync UI work showed this); frequency grouping is a natural reduction.

**Rejected**: collapse ALL actions into a menu. Reasons: refresh and sync are used frequently; making them require a menu click is friction.

**Rejected**: build an Alpine dropdown menu. Reasons: HTML `<details>` is zero-dependency, accessible by default, keyboard-navigable, and works in iframes. We don't need a custom dropdown.

**Rejected**: vertical icon column / sidebar. Reasons: this is a horizontal app, not a tabbed app. Header layout matches the existing pattern.

### 11. CORS for Yahoo Finance: documented as a known limitation

**Yahoo's `query1.finance.yahoo.com` does not send CORS-permitting headers for arbitrary origins. The implementation will likely need a fetch proxy (self-hosted tiny proxy, or a public CORS-anywhere mirror), OR the user accepts that refresh may not work in modern browsers until Yahoo adds CORS.**

This is intentionally **not** a blocking decision in this ADR. The detailed options are:

- **Public CORS proxy** (cors-anywhere, allorigins, etc.) — fragile, third-party dependency
- **Self-hosted tiny proxy** — Cloudflare Worker / Vercel function, $0 on free tier, but adds a backend (violates the "no backend" constraint of [ADR 0007](0007-v1-web-storage-localstorage.md))
- **Browser extension** — CORS disabled in extension context
- **Wait for change** — unlikely

A later ADR or ticket should resolve this. For now, the spec describes the implementation; the user can pick the proxy approach when they implement.

## Consequences

### Positive

- One click refreshes the entire portfolio; 5x retry handles transient errors silently
- Day Δ% + 52W range bar give at-a-glance portfolio dynamics
- Escape hatches: form override (any field), conditional retry button (failed symbols), manual edit (UI off)
- Schema size is small (3 new fields per holding); migration is non-destructive
- Implementation is testable (`lib/yahoo.js` takes a fetch function for DI)

### Negative

- **Yahoo dependency**: relies on unofficial API that can break anytime. ADR 0001 already notes this; v1.1 deepens the dependency.
- **Auto-retry wait**: up to 30s in worst case if all 5 retries fail. Mitigated by cancel-by-click.
- **Manual override vs refresh conflict**: a user who edits a price manually will lose the edit on next refresh. The override is documented but not warned-at-the-moment.
- **CORS**: Yahoo does not support browser CORS. Implementation will need a proxy — see decision #11.
- **Silent-drop on Yahoo response**: a symbol that doesn't exist (typo, delisted) is silently missing from the response. We treat "missing" as "failed." This is correct behavior but invisible to the user until the red badge appears.

### Trade-offs accepted

| Choice | Trade-off |
|---|---|
| Unofficial Yahoo API | No API key, no quota; can break anytime |
| Auto-retry 5x vs fail-fast | Better UX for transient errors; longer worst-case wait |
| Bulk vs per-row refresh | Simpler UI, fewer API calls; less granular control |
| Partial success vs all-or-nothing | Better UX for many-symbol portfolios; requires UI to surface failures |
| Manual override + silent overwrite | Escape hatch always works; user can lose edits |
| Lazy populate + UI hint | Existing v1.0 portfolios upgrade seamlessly; requires UI to nudge refresh |
| Load-time version bump | Reflects actual schema state; v1.0 files appear "fresher" than before |
| HTML `<details>` for menu | Zero deps, accessible; less customizable than a custom dropdown |
| Snapshot unchanged + intraday warning | Keeps schema small; requires UI to display warning |

## Rejected options (consolidated)

- **Per-row refresh button** — UI clutter, encourages single-symbol refreshes
- **Auto-refresh on page load or timer** — silent network calls, contradictory to "manual is intentional"
- **Per-symbol fetch (N+1 calls)** — unnecessary latency
- **All-or-nothing refresh** — one bad ticker blocks all
- **No retry on failure** — silent failures
- **Persist `refresh_failed` as a schema field** — schema bloat, survives reload incorrectly
- **Warn before overwriting manual values** — friction, breaks one-click promise
- **Read-only form fields** — defeats escape hatch
- **Block snapshot during intraday** — second-guesses user intent
- **3 raw numeric columns (52W high/low/prev_close)** — visual noise
- **Custom Alpine dropdown menu** — unnecessary deps
- **Public holiday API** — Yahoo's `marketState` already covers it
- **Hardcoded exchange hours** — DST math, holiday handling, per-exchange tables

## Deferred / future

- **Live price streaming** — 5-15 min TTL still applies; no WebSocket
- **Auto-refresh on page open** — defer to v1.2+
- **Snapshot UI** — separate v1.1 roadmap effort (this ADR explicitly does NOT include the snapshot UI feature, only the snapshot-related schema and intraday decision)
- **CORS resolution** — see decision #11; needs a separate ticket
- **Push notifications for price alerts** — out of scope
- **Historical chart of 52W range over time** — out of scope
- **Ticker auto-detection / correction** — user still types manually
- **Per-symbol refresh button** — rejected
- **Mobile breakpoint specifics** — implementation detail
