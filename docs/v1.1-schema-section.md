## 1. `holdings[]` additions

Three new fields per holding. Additive, optional, nullable.

| Field | Type | Default | Source (Yahoo) | Currency | Notes |
|---|---|---|---|---|---|
| `high_52w` | number \| null | `null` | `fiftyTwoWeekHigh` | Native (holding's `currency`) | 52-week high |
| `low_52w` | number \| null | `null` | `fiftyTwoWeekLow` | Native | 52-week low |
| `prev_close` | number \| null | `null` | `regularMarketPreviousClose` | Native | Previous trading day's close |

### Notes

- **Type**: `number \| null`. `null` (JSON) is the explicit "no data yet" state — distinct from `0` (which would be a real value).
- **Currency**: same convention as `current_price` — each holding's native currency. Do NOT infer from ticker suffix; read from Yahoo response's `currency` field when populating.
- **Yahoo field name mapping** is explicit in the table so implementation can verify by re-reading research/02.
- **Persistence**: per-record timestamp merge (ADR 0004) handles new fields transparently. The fields follow the standard `updated_at` + `device_id` per-record merge logic.

## 2. `snapshots[]` schema — unchanged

Per the v1.1 grilling (Q13, Q14, Q15):

- Snapshot stores **only `current_price`** per holding
- **`high_52w`, `low_52w`, `prev_close` are NOT included** in snapshots
  - Reason: 52W high/low is a moving reference; cross-time charting is less meaningful than current_price across snapshots
  - Reason: prev_close duplicates info derivable from the previous snapshot's current_price
- Snapshot intraday handling: store + show UI warning "現在盤中，價格會波動，要繼續嗎？" before confirming (driven by `marketState`, see research/03). No schema change needed for this.

The existing `snapshots: []` field in v1.0 is reserved but unused in v1.0; its schema is finalized when the snapshot UI effort (separate roadmap item) lands. This ticket only confirms **no new fields are added to the snapshot schema by v1.1 price tracking**.

## 3. Migration rule (v1.0 → v1.1)

**Non-destructive.** Only adds fields with `null` defaults.

### Steps (executed on `load()`)

1. **Read file** — load v1.0 JSON from localStorage or Drive.
2. **Detect version** — if `version !== '1.1'`, the migration path applies.
3. **Shallow-merge with `defaultPortfolio()`** — ensures all v1.1 fields exist with their default values:
   ```js
   data = { ...defaultPortfolio(), ...data };
   // for each holding:
   data.holdings = data.holdings.map(h => ({
     ...h,
     high_52w: h.high_52w ?? null,
     low_52w: h.low_52w ?? null,
     prev_close: h.prev_close ?? null,
   }));
   ```
4. **Bump version on load** — see §4 below. After this step, `data.version === '1.1'`.
5. **Persist** — write back to localStorage and Drive. (Save can happen later; version bump is on load, not on save.)

### Edge cases

- **v0.4 → v1.1** users skipping v1.0: existing v0.4 → v1.0 destructive migrations still apply (cost / shares). The v1.0 → v1.1 step then runs as above. Two-stage migration, each stage idempotent.
- **Missing `holdings` field**: if a file has no `holdings` array (corrupt or partial), `defaultPortfolio()` provides `[]`.
- **Existing holdings with stale `current_price`**: kept as-is. User can manually re-fetch or wait for next refresh.

## 4. Version bump rule

**Load-time bump.** Per Q16:

> When a v1.1 app loads any portfolio file, the `version` field is set to `'1.1'` before the data is used for rendering or saved back.

### Rationale

- `version` field semantically means "what schema spec this instance conforms to"
- After `load()` + shallow merge, the in-memory data IS v1.1-shaped (new fields exist with NULL defaults)
- Therefore version reflects the actual state, not "what the user has done"
- Alternative "bump after first populate" was rejected because it conflates schema version with data state

### Implementation note

- Bump must happen BEFORE any save (auto-save, manual save, sync push)
- Bump is in-memory; persistence happens on the next save (which may be immediate, may be on next user action — depends on existing save trigger logic)
- Idempotent: if `version === '1.1'` already, no-op

## 5. Per-record merge — no change needed

ADR 0004 (per-record newer-wins by `updated_at`) handles the new fields transparently. Each new field is included in the per-record merge logic; whichever side (local or remote) has the newer `updated_at` wins for the entire record including the new fields.

No ADR change required.

## 6. Backward compatibility

- v1.0 apps loading a v1.1 file: extra fields are ignored. New fields are lost if the user edits and saves in v1.0.
- v1.1 apps loading a v1.0 file: handled by migration rule (§3).
- Cross-device sync: both sides must be on v1.1 to round-trip the new fields. Otherwise sync silently drops them (same as any unknown field).

## 7. Schema version: `'1.1'`

String. Semver-like. The next version after v1.0.
